# Pack dev tools

All tools run with the venv in `tools/.venv` from the repo root, for example
`tools/.venv/Scripts/python tools/smoke.py`. None of them are part of the pack (`/tools/` is in
`.packwizignore`). Generated state lives in `tools/.server` (headless test server) and `tools/.data`
(reports, recipe dumps); both are git-ignored. Recreate the venv with
`python -m venv tools/.venv` then `tools/.venv/Scripts/python -m pip install -r tools/requirements.txt`.

| Tool | What it does |
|---|---|
| `smoke.py` | Boots the pack on a headless NeoForge server with a fresh world, runs `/reload`, stops, and triages the logs. Also runs `smoke_checks.js` on the server (that GregTech's recipe-viewer mixins apply to the pinned JEI, and that every quest item task and FTB Filter System filter in the book loads). Exit code 1 on a crash, KubeJS error, or unknown error. |
| `startat_test.py` | Checks the `/startat` command on a fresh headless world: the start-point finder for a few real places, then the command itself as a non-op fake player (open water, first use, second use, bad input). Exit code 1 on any failure. |
| `logtriage.py` | Groups a log's warnings/errors, hides known-harmless ones (`known_issues.json`, each with a reason), and flags what's new since the last run. Default: the Prism client's `latest.log`; `--server` for the test server. |
| `pregen.py` | Pre-generates a fixed-seed area with Chunky (added to the test server for that run only) and reports chunks/second. `--place LAT,LON` centers it on a real-world spot in TFC: Real World. |
| `rocksample.py` | How far is igneous extrusive rock (andesite, basalt, dacite, rhyolite: what Create's andesite alloy needs) from a start, without generating chunks. A dev-only KubeJS script (`rocksample.js`) asks TFC's own rock generator on a fresh 20 m-per-block world, for each place's start: the rock, an estimate of the rock category, and the distance in blocks to the nearest extrusive surface rock and to the nearest reachable by digging ~100 blocks down, each also split into anywhere (land or seabed) and on dry land. `--places [NAME ...]` (default: 43 cities) or `--random N` (N land points worldwide, uniform by area, with the share that have extrusive rock within 500 to 25,000 blocks); `--rocks A,B,...` changes the target rocks (default the four extrusive ones, e.g. add `diorite`); `--validate world-rock-rome ...` checks the sampler against finished worlds. Report in `tools/.data/reports/rocksample-<timestamp>.json`. Uses the test server, so not while another tool does. |
| `worldgen_check.py` | Is the overworld's generation still frozen, so mods can be added or updated without a world wipe? Boots the test server on a fresh fixed-seed world at the pack's 20 m scale (about 2 minutes), fingerprints generation and compares it with the committed `worldgen_baseline.json`. Findings are **continuity-breaking** (seams in existing worlds: terrain, biomes, rock, carvers, veins, sea level, map; TFC and TFC: Real World changing is one by definition), **new-chunks-only** (a new feature, structure or spawn: each names the mod and how to strip it) or **info**; exit code 1 on the first two. Tier 0 reads the jars (worldgen data hashes, mixins into worldgen code; `--static` runs just this, in seconds), tier 1 the effective registries (generator, possible biomes, per-biome features, carvers and spawns, biome and structure modifiers and how many TFC biomes they reach, structures, tags, registry hashes, configs), tier 2 about 2,000 fixed points (TFC's own height, biome, rock and climate, no chunks generated). `--golden` adds tier 3: eight small areas generated with Chunky (added for the run only), compared per chunk (biomes, `tfc:chunk_data`, an underground rock, ore, air and fluid census) with checks that no foreign block, structure or entity appears; it is the only tier that sees code-level changes. Continuity-breaking changes are always refused. `--accept "<reason>"` folds new-chunks-only additions into the baseline with the mod, date and reason recorded; `--update --force-terrain "<reason>"` is the loud exception; plain `--update` makes the first baseline or takes info-only changes. Details in the script's docstring. Uses the test server, so not while another tool does. |
| `worldview/serve.py` | Browser viewer for a save: map (surface, height, TFC temperature/rainfall, lat/long grid), slices, Y distribution with host rock, chunk heatmaps. `--compare OTHER` adds a world B. Terrain far apart (after `/startat`) is split into areas, picked from a list; it opens on the player's. |
| `recipes/dump.py` | Dumps every recipe, tag and block loot table from the pack via a dev-only KubeJS script on the test server, into `tools/.data/dumps/`; `index.json` also counts GregTech's ore veins (how many still generate). `--label NAME` to tag a before/after dump. |
| `recipes/serve.py` | Recipe explorer: how anything is made or used, first route from the world, why something is unreachable, duplicate materials, progression rules (`recipes/progression.json`), and dump comparison. `--world` picks the world used as the starting point. |
| `quests/build.py` | Builds the FTB Quests book (`config/ftbquests/quests/`) from `quests/route.json`, then checks the route against the progression checker: every quest item exists and is reachable, and no quest comes before its prerequisites. Edit `route.json`, not the generated files. |
| `quests/pack_query.py` | Quest-writing lookups against the newest dump: an item's name, progression step and recipes (`item`), `search`, `tag`, `uses`. |
| `quests/port_tfg.py` | Ports TerraFirmaGreg's quests (LGPL-3.0): `fetch` pins its quest files at a commit, `extract` converts them to route.json's quest format with notes on what doesn't carry over, and `merge` applies the per-quest review (`quests/tfg_review/`, brief in `REVIEW.md` there) to `quests/route.json`. After the port, edit `route.json` directly; `merge` is for re-porting. |
| `gt_update.py` | Reports newer GregTech nightlies (commits in between, dependency check against the pack); `--apply` swaps the pack's pinned build. |
| `mod_report.py` | Available updates with changelogs, client/server side audit against Modrinth, and license flags for redistribution. |

Typical loops:

- After any mod or script change: `smoke.py`, then `recipes/dump.py` and check the explorer's Progression page, then `quests/build.py` (the route check uses the new dump).
- Before and after a KubeJS integration script: `recipes/dump.py --label before`, change, `recipes/dump.py --label after`, then *Compare dumps*.
- After a KubeJS, TFC: Real World or NeoForge update: `startat_test.py` too (the command leans on their internals).
- World generation changes: `pregen.py --fresh --seed same-seed`, then `worldview/serve.py tools/.server/world-pregen --compare <older copy>`.
- After adding or updating any mod: `worldgen_check.py` (about 2 minutes); it must pass, or its findings say what to strip or accept. Before a release: `worldgen_check.py --golden` (about 3), the only run that sees code-level changes in generation. A reviewed new-chunks-only addition goes into the baseline with `--accept "<reason>"`, info-only differences with `--update`; commit `worldgen_baseline.json` with a message saying why.
